# Conformance and performance

The execution report joins language fixtures with tests that need a simulator
host, C VPI application, or independent numerical reference. Every credited
result comes from the measured run. Skipped tests, expected failures and missing
execution remain visible.

## Run it

```sh
nix develop -c python3 tools/conformance.py run
```

Each run writes a fresh directory under `.zig-cache/conformance/`: `report.md`,
`report.json`, per-test verdicts and suite logs. The report records the commit,
time and a hash of the actual source, including uncommitted edits. CI runs the
same command and publishes the complete `execution-results` artifact.

See [the test guide](https://github.com/OmarSiwy/VerA/blob/main/tests/README.md)
for focused commands, fixture conventions and registering specialized tests.

The fixtures are the
[VAMS Conformance Suite](https://github.com/OmarSiwy/VAMS-Conformance-Suite),
checked out as the `tests/conformance` submodule: its `tests/` holds the
Verilog-A, Verilog-AMS, IEEE 1364 and Annex E fixtures by language and
chapter, and its `vera/` the hosts, canaries, ledgers and expected failures
only VerA uses. Fetch it once after cloning:

```sh
git submodule update --init tests/conformance
```

## Reading coverage

A **covered** clause has a passing test that exercises it. A clause with a
failing or expected-failing test is **failing**, even if other tests pass.
An **unsupported** clause retains that classification when rejection tests pass.
**Not run** means a test is registered but has no passing execution result;
**uncovered** means a testable clause has no registered test. **No fixed
oracle** means `GAPS.tsv` dispositions the clause as non-normative, optional or
explicitly unspecified: there is no unconditional executable outcome to assert,
so it is neither a missing test nor a failure. The JSON links every clause to
its fixtures and specialized assertions and separates positive from rejection
coverage. A rejection demonstrates enforcement of a prohibition, not support
for that construct.

The denominator includes all inventoried clauses, with classifications such
as non-normative, optional and unsupported listed separately. No classification
is silently counted as a passing test. Host and reference tests can cover a
clause without an HDL fixture, provided their exact registered assertions ran
and passed. The uncovered column excludes clauses reported as no fixed oracle;
their rows remain in the denominator but do not contribute to a failure count.

The command's exit status is a regression gate, not a claim of complete
conformance. Declared expected failures remain visible in the report; unexpected
failures or incomplete execution records fail the command.

Clause coverage does not establish that every rule or possible language program
conforms. The [AMS requirement ledger](https://github.com/OmarSiwy/VAMS-Conformance-Suite/blob/main/vera/ledger/OBLIGATIONS.tsv)
tracks individual normative sentences, with stronger evidence levels. A bare
clause citation cannot cover every sentence it contains. IEEE 1364 currently
has a clause inventory rather than a sentence ledger.

## Historical release measures

`python3 tools/conformance.py` retains the older release table used by
`--changelog` and `--check`. Its A measure is fixture execution; B and C are
**static citation inventories**, not execution-backed conformance scores.
Release entries in `CHANGELOG.md` keep their original meaning.

The [verdict baseline](https://github.com/OmarSiwy/VAMS-Conformance-Suite/blob/main/vera/ledger/VERDICTS.tsv)
is compared by fixture name in CI. A change in verdict must be investigated
and recorded explicitly. The stricter nightly checks still perturb assertions,
check derivatives, and track sentence-level evidence.

## The live report

The [conformance and speed report](https://omarsiwy.github.io/VerA/report/)
is rebuilt from scratch on every push to `main`. It holds the
clause-by-clause map of which fixture covers which rule,
the open gaps and defects, the compile-time distribution, and the speed of
the generated devices' `eval`.
